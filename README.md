# workflows

Shared reusable GitHub Actions workflows for the OBS Studio plugin snaps in
the `obs-plugins-snaps` organization. The individual plugin snap
repositories call these workflows from their own CI, so each plugin repo
only contains a small caller workflow instead of a full copy of the build
logic.

GitHub requires reusable workflows to live in the `.github/workflows/`
directory of the repository that hosts them, hence the nested path here.

## Available workflows

### `build-snap.yml`

Packs the snap in the calling repository and uploads it as a build
artifact. The artifact name is prefixed with the `plugin_name` input so
that artifacts from several plugin snaps can be told apart.

Intended to run on pull requests and pushes to branches other than
`main`; for releases from `main`, use `release-to-edge.yml` instead, which
also packs the snap.

Inputs:

| Input         | Required | Description                                             |
| ------------- | -------- | ------------------------------------------------------- |
| `plugin_name` | yes      | Upstream plugin project name, used in the artifact name |

### `release-to-edge.yml`

Packs the snap in the calling repository and releases it to the
`latest/edge` channel of the Snap Store. Intended to be called on every
push to `main`, so that edge always tracks the current development state.
Prints the uploaded revisions in the workflow summary.

Inputs:

| Input         | Required | Description                                                                |
| ------------- | -------- | -------------------------------------------------------------------------- |
| `plugin_name` | yes      | Upstream plugin project name; the snap name is `<plugin_name>-obs-studio` |

Secrets:

| Secret                  | Description                                                                                     |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| `SNAPCRAFT_STORE_EDGE`  | Snap Store credentials with permission to upload and release to `latest/edge` for the snap.      |

### `promote.yml`

Promotes already uploaded revisions of the snap to a risk level chosen by
the maintainer (`beta`, `candidate`, or `stable`). Intended to be called
on `issue_comment` events. A maintainer comments:

```
/promote <revision> <risk-level>
```

where `<revision>` is a store revision number (or a comma-separated list
of them), or the shortcut `latest` (the newest revision currently in
`latest/edge`), and `<risk-level>` is one of `beta`, `candidate`, or
`stable`. For example:

```
/promote 42 candidate
/promote 42,43 latest/stable
/promote latest stable
```

The command is acknowledged with a 👀 reaction, and the outcome is
reported as a comment on the same issue. Only collaborators with write
access to the repository can promote.

Inputs:

| Input         | Required | Description                                                                |
| ------------- | -------- | -------------------------------------------------------------------------- |
| `plugin_name` | yes      | Upstream plugin project name; the snap name is `<plugin_name>-obs-studio` |

Secrets:

| Secret                          | Description                                                                                              |
| ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `SNAPCRAFT_STORE_CREDENTIALS`   | Snap Store credentials with permission to release the snap to `beta`, `candidate`, and `stable`.          |

## Usage

From a plugin snap repository (as generated by the copier template in
`obs-plugins-snaps/template`):

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:
  issue_comment:
    types: [created]

jobs:
  # Pull requests: build only.
  build:
    if: github.event_name == 'pull_request'
    uses: obs-plugins-snaps/workflows/.github/workflows/build-snap.yml@main
    with:
      plugin_name: "source-record"

  # Every commit to main: release to latest/edge.
  release:
    if: github.event_name == 'push'
    uses: obs-plugins-snaps/workflows/.github/workflows/release-to-edge.yml@main
    with:
      plugin_name: "source-record"
    secrets: inherit

  # Maintainers promote edge revisions by commenting on issues.
  promote:
    if: github.event_name == 'issue_comment'
    uses: obs-plugins-snaps/workflows/.github/workflows/promote.yml@main
    with:
      plugin_name: "source-record"
    secrets: inherit
```

Reusable workflows must be referenced with a full ref (`@main` above), and
callers cannot add `runs-on` or `steps` to the calling job. Because the
workflows above reference store credentials directly, callers must pass
`secrets: inherit`.

## Differences from the snapcrafters CI model

This setup is inspired by the
[snapcrafters](https://github.com/snapcrafters/ci) release and promote
workflows (see
[obs-plugins-snaps/meta#6](https://github.com/obs-plugins-snaps/meta/issues/6)),
but it differs from them in important ways:

- **Trigger: `main` vs a `candidate` branch.** Snapcrafters repos build
  and release whenever something lands on a long-lived `candidate`
  branch, which is kept in sync with upstream. Here, every commit pushed
  to `main` is released to `latest/edge`; there is no release branch to
  maintain.

- **First stop: `edge` vs `candidate`.** Snapcrafters releases new builds
  to `latest/candidate` and gathers structured feedback in a
  "call for testing" issue (including a bot that collects screenshots).
  Here, builds land in `latest/edge` first and testing feedback happens
  organically; no call-for-testing issue, screenshot bot, or per-revision
  git tags are created.

- **Local builds vs Launchpad remote-build.** Snapcrafters snaps target
  many architectures that GitHub runners cannot build for, so they use
  `snapcraft remote-build` on Launchpad (which requires Launchpad
  credentials). Plugin snaps in this organization are core24 and amd64
  only (see the copier template), so they are built locally on the
  runner with `canonical/craft-actions/snapcraft/pack`, and no Launchpad
  secret is needed. If a plugin snap ever adds architectures not covered
  by GitHub runners, this is the piece that would have to change.

- **Generic promotion vs a fixed ladder.** Snapcrafters promotion is
  narrow by design: `/promote <revisions> latest/stable [done]` only
  works on the call-for-testing issue, only promotes revisions listed in
  that issue, and closes it when `done` is passed. Here, promotion is a
  general-purpose tool: a maintainer can promote any edge revision
  (including `latest`) to `beta`, `candidate`, or `stable`, from any
  issue, without a preceding call-for-testing workflow.

In short: the snapcrafters model is built around a controlled
candidate → stable pipeline for high-traffic, multi-architecture snaps;
this one optimizes for a small, single-architecture organization where
edge tracks `main` and maintainers decide per release how far a revision
should go.
